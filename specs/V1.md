# V1 — scope

V1 is the smallest Arrflix a friend can use against a real server: they request a movie or a show, it arrives, and they're told. This page holds **scope only**: what's in, what's out, and what V1 is judged by. Progress lives in the GitHub `V1` milestone; verification lives in tests named for the REQ IDs below.

**V1 is done when every REQ ID listed under _In_ has a passing test named for it.**

Every item here is decided. A change to V1's scope is a PR against this page.

### Roles and permissions (decided)

Overseerr-style. Two fixed perspectives, **operator** and **requester**; each screen is designed for exactly those two. A small set of per-user settings: **auto-approve on/off**, **4K allowed**. The authz engine stays internal for enforcement; no role editor.

Per-user toggles are user-subject grants layered over the requester baseline, so no new schema is needed. Auto-approve grants `requests.auto_approve:*` for the user's tiers. 4K grants `requests.create:*:4k`.

- **REQ-ROLE-001:** Every user holds exactly one role, `requester` or `admin`. Invites and role editing offer only those two.
- **REQ-ROLE-002:** Any screen both audiences see must render for exactly two perspectives, operator and requester. The perspective comes from the user's role, not from individual permission keys.
- **REQ-ROLE-003:** Perspective is presentation only. Every action must still be enforced by permission key on the backend, so a UI perspective never grants a capability.
- **REQ-ROLE-004:** An admin must be able to set, per user, whether their requests are auto-approved. One toggle covers every tier the user may request. When it's off, requests enter the approval queue.
- **REQ-ROLE-005:** An admin must be able to set, per user, whether they may request 4K. It governs which tiers are offered.
- **REQ-ROLE-006:** An operator with a live request of their own sees the operator perspective plus their request's state.

- **`co_admin` and `viewer` hidden (decided).** Invite and role pickers offer only `requester | admin`. The seeded rows stay, and no users hold them, so no migration is needed. A browse-only viewer would add a third "requester who can't request" case to every screen. A co-admin is an operator minus one permission.
- A trusted approver who isn't an operator is deferred; see _Out — later_.

### Path mapping

Blocks any deployment where the downloader and Arrflix mount storage at different paths. It isn't needed for a shared `/data` layout, which is the owner's own setup. The slice is a subset of the [path-mapping spec](./modules/path-mapping/README.md):

- The volume model and resolver as specified, with **downloader aliases only**.
- Two boundaries: downloader → Arrflix (import) and Arrflix → downloader (save path).
- Manual authoring, with a `Test` action that reports path existence and hardlink feasibility (same device).
- Auto-detection tier 1 only: detect that no mapping is needed.

Deferred: media-server boundaries (with the V1.1 Plex work), and auto-detection tiers 2–3.

- **REQ-PATH-001:** A file the downloader reports at its own path must be imported from the correct Arrflix path.
- **REQ-PATH-002:** When routing sets a save location for a grab, the grab must tell the downloader where to save, in the downloader's own frame. The save location is a routing action, with a default that is unset out of the box. Unset sends no save path, so the downloader's own default applies.
- **REQ-PATH-003:** An install where every actor sees the same paths must need no path configuration.
- **REQ-PATH-004:** An operator must be able to verify a mapping before relying on it, including whether imports will hardlink or copy.
- **REQ-PATH-005:** A path that can't be resolved must fail visibly at import, never silently misplace or skip a file.

### Hardlink inode capture — [Hardlinks](./modules/hardlinks/README.md)

Hardlinking itself is built: the importer links, falls back to a copy, and records the method. V1 adds only the capture that the reference graph is later built from, so the history exists when hygiene arrives. It adds no extra I/O, because the three fields come back from `stat()` calls import and scan already make. The graph queries, downloader correlation and exact broken-link detection are deferred.

- **REQ-LINK-001:** Every file Arrflix imports must have its device, inode and link count captured from the post-link `stat()`.
- **REQ-LINK-002:** Every file a scan or verify re-stats must have those facts refreshed.

### Not out yet — [Not out yet](./stories/09-not-out-yet.md)

REQ-UNREL-001, 002, 003, 004, 006, 009

Episodes already gate on air date. Movies need a persisted obtainable date (TMDB digital/physical release) that the cadence respects. Without it, an in-cinema film reads as "searching" and polls indexers daily for months.

### Deployment hardening

Defects the drift pass found that break real use outside the dev setup. Two are already covered: approve and deny racing is REQ-APPROVE-006, and cancelling an in-flight download is REQ-CANCEL-004.

- **REQ-HARD-001:** A fresh install without the dev seed must be able to complete a grab.
- **REQ-HARD-002:** Disabling a user must end their access: refresh must refuse inactive users, and disabling must revoke their sessions.
- **REQ-HARD-003:** A downloader that is unreachable must leave its jobs retryable. It must never fail them as non-retryable, which blocklists good releases.
- **REQ-HARD-004:** A canceled download job must never be imported later, and must stay identifiable in the downloader, so the user can find and remove what Arrflix abandoned. Canceled torrents are tagged `arrflix-canceled`.
- **REQ-HARD-005:** Every torrent Arrflix adds must carry the `arrflix` category, so the user's downloader seeding limits can be scoped to Arrflix's torrents.

**Torrent removal is the user's (decided).** Once Arrflix hands a torrent to the downloader, it never removes it, on cancel or after import. Seed files stay after a normal import anyway, and removing a partial download from a private tracker risks hit-and-run penalties. The lifecycle belongs to the downloader's own seeding limits.

## Out — V1.1

- **Notification → watching (REQ-FULFIL-006): decided.** This needs Plex library integration: trigger a scan after import, resolve the item's Plex ID, and fill the deep-link field the notification payload reserves. The only existing Plex code is SSO. Until then, the notification opens the Arrflix title page, and Plex's own library watching picks up the hardlinked file.

- **Search history (REQ-SEARCH-004, 005): decided.** Record what each search considered and why each candidate was rejected, including searches that found nothing and which indexers answered. It's a new subsystem (per-release decision storage), and it answers the owner's "why isn't this downloading?"

## Out — later

- **Storage quotas: V2 (decided).** Replace the auto-approve toggle with a per-user GB quota over a rolling 30-day window. The shape:
  - **Rule:** every grab is checked against remaining quota when a release is picked. If it fits, it proceeds. If not, it's held for the owner as a proposal with reason "over quota".
  - **Exception:** new episodes of an already-approved tracking count toward quota but are never held.
  - Settings: unlimited = auto-approve on; 0 = auto-approve off; N GB is the normal case.
  - Declines read "the owner declined". The hold carries the reason. No re-request cooldowns, and no hard stop, since over-quota users can keep requesting into holds.
  - Later still: auto-release holds as the window frees.
  - Known shift: V1 approves at request time, V2 at grab time.
- **Approver toggle: decided, deferred.** A trusted user who approves but doesn't run the server is a **requester plus a per-user "can approve requests" toggle**, not a third perspective. Perspective only matters on screens both audiences share, and the approval queue is approver-only. The toggle grants the existing `requests.approve:*`, `requests.deny:*` and `requests.view.any` keys and unlocks the queue page and approval notifications. Approvers seeing who asked is expected for that role. In V1 the owner approves everything.
- **Seed lifecycle rules.** Per tracker and downloader, set seed ratio and time on add, and optionally let Arrflix remove the torrent when they're met. Routing rules already evaluate each grab with the indexer and downloader in hand, so this is an extension of them. It pairs with hygiene and the hardlinks graph.
- **Custom roles.** Decided out; the pull toward them was completeness, not a use case. Roles can become presets (keys + perspective) if one ever appears.
- **Deferred stories:** [Multi-requester scope union](./stories/05-multi-requester-scope-union.md), [Upgrades and divergent tiers](./stories/06-upgrades-and-divergent-tiers.md), [Autonomy and proposals](./stories/08-autonomy-and-proposals.md) (except what V2 quotas reuse), [Indexer health](./stories/10-indexer-health-degraded-and-recovery.md).
- **Deferred requirements from in-scope stories:** REQ-SERIES-007, 008; REQ-APPROVE-002, 004, 009, 010, 011; REQ-CANCEL-003 (with scope union), 010 (true by omission), 011 (with proposals); REQ-SEARCH-006, 007, 008, 010, 011; REQ-UNREL-005, 007, 008, 010, 011 (008 moves to V1.1 if metadata refresh doesn't already re-read the date).
- **Series stand-down (REQ-SERIES-004): decided, deferred with upgrades.** Searches already stop once every in-scope want has a file, so the only V1 symptom is a completed tracking staying `active`. The archive transition is defined in terms of upgrade watching ("done and not looking for better"), so it ships with [Upgrades and divergent tiers](./stories/06-upgrades-and-divergent-tiers.md).
- **Work dispatch (`LISTEN/NOTIFY` wake-ups): decided, deferred.** Workers already claim with `FOR UPDATE SKIP LOCKED` on 2–3s tickers, so correctness is in place. The missing wake-up costs seconds of latency in a flow measured in minutes.
- **Deferred modules:** hygiene, hardlinks graph queries, media-server propagation, connectivity health, calendar, watchlist, additional downloaders.
